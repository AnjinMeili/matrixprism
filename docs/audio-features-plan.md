## The question

The composer's audio analysis is its own code on top of the Web Audio API's
`AnalyserNode` (see "Frame pipeline" and "Tempo model" in
[composer-spec.md](composer-spec.md), and "Audio" in the
[composer README](../composer/README.md)). Its
BPM detection follows bass energy only and its key detector is a simple
profile match; neither has been measured against real music. Two things
are worth knowing:

1. **The data we have.** Would a library give better beats, BPM and key, and
   comparable bands and level?
2. **The data we do not have.** Would features such as spectral centroid,
   flux, flatness, chroma, MFCCs, loudness or onsets give the patterns
   something worth using?

And for each, is it worth the cost in code, load size, CPU time and licence?

## The candidates

Checked on 2026-10-13 from the npm packages themselves (listed and searched,
not run).

| | Web Audio alone (today) | Meyda 5.6.3 | Essentia.js 0.1.3 |
| --- | --- | --- | --- |
| Licence | Ours, GPL-3.0 | MIT | AGPL-3.0; UPF also sells commercial licences for Essentia |
| Last published | – | April 2024 | June 2021 (corrected 2026-10-14; see Risks) |
| Size | – | 0.5 MB package; one minified browser file | 10 MB package, of which about 2 MB is WebAssembly and 2.5 MB its JavaScript loader |
| What it computes | FFT spectrum and waveform (browser); bands, level, beat, BPM, key (our code) | 20 frame features: RMS, energy, ZCR, power spectrum, spectral centroid, crest, flatness, flux, kurtosis, rolloff, skewness, slope and spread, chroma, loudness, mel bands, MFCC, perceptual sharpness and spread | 202 algorithms, among them `RhythmExtractor2013`, `BeatTrackerMultiFeature`, `PercivalBpmEstimator`, `TempoTapDegara`, `KeyExtractor`, `HPCP`, `Chromagram`, `OnsetDetection`, `SuperFluxExtractor`, `NoveltyCurve`, `LoudnessEBUR128`, `Danceability`, `MFCC` |
| BPM, beats, key | Yes, hand-written | No | Yes, published research algorithms |
| Live use | `AnalyserNode` in the page's frame loop | Its live analyser uses `ScriptProcessorNode`, which browsers have deprecated; `Meyda.extract()` also works on sample arrays we hand it | No audio node of its own: it works on sample arrays, so live use means feeding it from an `AudioWorklet` or the frame loop. The tempo and key extractors work on a whole signal, so live use means running them over a sliding window |

Two consequences shape the plan:

- **Most of Meyda's features are a few lines of arithmetic on the spectrum
  the `AnalyserNode` already gives.** So "Web Audio alone" in this comparison
  includes hand-written versions of the simple ones (centroid, flux,
  flatness, rolloff, ZCR). That separates "is this feature useful to a
  pattern" from "do we need a library to get it". Meyda would earn its place
  mainly for chroma, MFCC and perceptual loudness, which take more care.
- **Essentia.js is the only candidate that competes with our beat, BPM and
  key detection.** Its value is there, and so is its cost: size, an older
  release, and the licence.

## Test material

   - click tracks from 70 to 180 BPM, steady, swung and changing tempo;
   - chords and scales in each of the 24 keys;
   - sine sweeps and band-limited noise, for the bands and the level;
   - silence, noise and drums alone, which should produce no key.
2. **Anjin's music, with known BPM and key.**
   - **What:** 30 to 50 tracks across the genres played, tagged by DJ

   - **Where:** the files stay on Anjin's machine and are never committed;
     the harness reads a folder named on the command line.
   - **How far to trust the tags:** they are another program's estimates, so
     the report gives agreement with them rather than accuracy. The beat can
     be spot-checked with tap tempo (T19).
3. **A live check at the end**, by Anjin, with music through the composer
   and the chosen setup, in Safari.
4. **The Beatport EDM Key Dataset** (Ángel Faraldo, 2017,
   [doi:10.5281/zenodo.1101082](https://zenodo.org/records/1101082)), which
   Anjin offered on 2026-10-13 to download and set up.
   - **What:** 1,486 two-minute excerpts of EDM from Beatport previews, each
     with a key label annotated by hand, a confidence level and comments.
     CC BY-SA 4.0. No BPM or beat annotations on the record page; whether
     `original_metadata.zip` holds Beatport's BPM is to be checked.
   - **Where:** outside the repository on Anjin's Mac; the path is still
     to come. The audio is never committed; figures from it may be, with the
     citation (the DOI and Faraldo's 2017 PhD thesis, *Tonality Estimation
     in Electronic Dance Music*, Universitat Pompeu Fabra).
   - **Use:** key only. Excerpts labelled ambiguous or changing key are left
     out using the spreadsheet's confidence and comments.
   - **Caveat:** Faraldo built it at Pompeu Fabra, where Essentia is made,
     for the thesis that produced Essentia's EDM key profiles. Essentia may
     do better here than on other music; the report says so and shows its
     EDM and general profiles apart.

## The harness

A tool beside the colour measurement, run through `tools/headless.mjs`:
`npm run compare-audio -- --folder <path>`, with `tools/audio-compare.mjs`
and `tools/audio-compare.html`.

- **Reading the audio.** Each file is decoded and played through an
  `OfflineAudioContext`. The context is suspended every thirtieth of a second
  to read analysers set up as the composer's own: 2048-point FFT with
  smoothing 0.55 for bands and beats, 8192 points for key. The composer's
  own code then runs on what was read: the band, level and beat logic in
  `audio.js`, `TempoTracker` and `KeyDetector`. Offline, the result is the
  same on every run.
- **Meyda.** Each thirtieth of a second, the same 2048-sample frame goes to
  `Meyda.extract()` and to the hand-written equivalents.
- **Essentia.js.**
  - **Whole track:** `RhythmExtractor2013` gives BPM and beat times, and
    `KeyExtractor` gives the key and its strength.
  - **As it would run live:** the same two over sliding 10-second windows,
    which also gives the time each takes to settle.
  - **Onsets:** `SuperFluxExtractor`, against our bass-jump beats.
- **Output.** For each track, one row per frame for each source, plus a
  summary; then a Markdown report in `docs/`, as for the colour analysis.

One change to the composer first: `AudioAnalyzer` owns its own audio
context, so the step that turns analyser data into features has to be
callable with data from elsewhere. That refactor comes with tests.

## What is measured

**The data we have:**

| Measure | How |
| --- | --- |
| BPM | Share of tracks within 2% of the reference; halving and doubling errors counted apart; time to lock; changes per minute once locked |
| Beats | F-measure with a 70 ms window, against the click tracks' known beats |
| Key | Exact match; compatible match (Camelot ±1, or relative major/minor); time to the first key; changes per minute; keys claimed on noise and drums |
| Bands and level | Agreement of bass, mid, treble and level with Meyda's loudness and RMS over the same ranges: a sanity check, not accuracy |

**The data we do not have.** Each feature is plotted over a few tracks, with
the music's sections marked, and kept only if all of these hold:

- **It moves with the music** in a way a pattern could show, and is steady
  enough at 30 frames a second.
- **It is new information:** its correlation with level, bass, mid and treble
  is below 0.8.
- **A pattern has a use for it:**
  - centroid, as the music's brightness, for colour;
  - flux or onsets, for better beat detection than bass jumps;
  - flatness, telling noise from tone, to keep drums from producing keys;
  - chroma, as twelve pitch levels, compared with the key detector's own;
  - MFCCs, as timbre, for section changes, compared with `tempo.js`'s
    bar-to-bar spectrum comparison;
  - loudness, as a perceived level.

**Cost:**

- **Time:** milliseconds per frame for each pipeline in Chrome, and in Safari. A 30 fps frame is 33 ms; the aim is under 2 ms of
  analysis per frame on the development Mac.
- **Size and start-up:** load size, and the time to start (Essentia's
  WebAssembly).
- **Memory.**

## Draft decision rules

- **Beat and BPM:** replace ours with Essentia's only if the licence is
  accepted and it is right (within 2%) on at least 20 more tracks in every
  100 of Anjin's music, and settles fast enough to use live.
- **Key:** the same, with at least 15 more in every 100 exact or compatible.
- **Simple features** (centroid, flux, flatness, rolloff, ZCR): write them
  ourselves, if a pattern will use them.
- **Meyda:** take it only for chroma, MFCC or loudness, and only if a pattern
  will use them.
- **Otherwise** keep Web Audio alone and tune what we have, starting with the
  constants the comparison shows to be off.

## If something is adopted

- **No bundler:** the browser build would be copied into
  `composer/public/vendor/` with its licence. The server serves only
  `public/`, and should stay that way.
- **Live analysis:** in our frame loop or an `AudioWorklet`, not Meyda's
  `ScriptProcessorNode` analyser. Essentia in an `AudioWorklet` or a worker,
  with windowing for tempo and key.
- **New data for patterns:** uniforms such as `u_centroid`, `u_flux` and
  `u_flatness`, and a chroma texture, added to the pattern interface in the
  spec.
- **Tests:** the harness's figures for the synthetic signals become test
  fixtures.
- **Tasks:** each adoption is its own task, on its own branch.

## Risks

- **The tags are not truth.** Two programs agreeing does not make them right.
- **Offline is not live.** Microphone and loopback input add noise and delay.
  The live check is there for that.
- **Essentia.js has not been released since June 2021.** Looked at on
  2026-10-14: 0.1.3 was published to npm on 24 June 2021. The npm entry's
  "modified" date of May 2022, given here before, is not a release. The
  default branch's last commit is from July 2022. The repository is not
  archived and has demo branches updated as late as December 2025 (a demo
  redesign, a MAEST model test, genre tagging). So it is a live research
  project with an old library release.
- **Safari is where it has to work.** The comparison runs in Chrome; Safari's
  WebAssembly and `AudioWorklet` performance is checked only at the end, by
  Anjin.
